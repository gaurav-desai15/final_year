D1  --  Speed and instrumentation                          commit 694a1ae
--------------------------------------------------------------------------------
Goal: everything downstream depends on run speed; instrument before optimising.

Changes
  * models.RunStats: six per-stage wall-clock timers (clone, cpg-build,
    cpg-load, context, dataflow, llm). `stage_breakdown()` omits unmeasured
    stages. `analyze` prints a timing table; the Markdown report lists it.
  * cli.py: removed the `or source_calls` fallback that fed EVERY source in
    the repo into Joern's `reachableByFlows` (the most expensive operation)
    when a function had no source call of its own.
  * Content-addressed CPG cache: cpg.bin is stored under the work dir named
    by `repo_manager.source_fingerprint()` -- a SHA-256 over the CONTENT of
    every source file, not the commit SHA. Rationale: the mutation harness
    rewrites tracked files in place without committing, so every mutant of an
    app shares its SHA; a SHA-keyed cache would hand every mutant the
    unmutated CPG and silently invalidate the whole evaluation. Re-running
    the same tree now skips joern-parse. `keep_cpg` defaults true;
    `--no-keep-cpg` opts out.

Instrumented baselines (qwen2.5-coder:7b, on the real machine)
  * bundled python example : ~110s total, LLM ~88s
  * OWASP NodeGoat, --no-dataflow, 15 contexts : ~270s total, LLM ~262s (97%)

Finding that shaped the rest of the work: Joern is already ~8s end to end.
The <=90s/run target cannot be reached by touching Joern -- it is entirely the
LLM invocation (prompt length, output length, context count, concurrency).
The absence-mode prompt (D2) is deliberately shorter for this reason.

D2  --  Control-absence analysis mode                      commit 52e237b
--------------------------------------------------------------------------------
Goal: a second detector asking "does a sensitive operation run WITHOUT an
access control that should be there" -- a control-dependence question, not a
taint question, so no dataflow.

New: rules/control_absence.yaml
  * `triggers` per language: operations that plausibly need a control --
    Express/Flask route registrations, DB reads/writes, file sends, credential
    handling. Each carries an `operation` tag (route|db_read|db_write|
    file_send|credential|session).
  * `guards` per language: syntactic evidence a control IS present -- auth
    middleware, role checks, ownership comparisons, session guards, validators.
    Each carries a `control` tag (authentication|authorization|ownership|
    session|validation).
  * Header documents the deliberate inversion vs sinks_sources.yaml: sink
    patterns must require invocation syntax so bare property access never
    mislabels code; GUARD patterns deliberately match bare property access
    (`req.user`, `req.session.userId`) because the failure mode is inverted
    (a missed guard makes us over-report).

rules.py: `ControlRule`, `AbsenceRules`, `load_absence_rules()`.

models.py
  * `ControlTrigger` and `GuardEvidence` -- each carries the CPG call node id
    and line, so a finding is checkable back against the graph.
  * `FunctionContext` gains `control_triggers`, `guard_evidence`.
  * `to_absence_prompt_text()` -- renders an empty guard list as an explicit
    "(none)". Absence is a field, not an inference.

context_extractor.py
  * `find_control_triggers()` -- pure-python match over the flat call list,
    same shape as `find_sink_candidates()`.
  * `collect_guard_evidence()` -- guards on the handler body + its real
    call-graph callers. Express route handlers are PASSED AS ARGUMENTS to
    `app.get(path, mw, handler)` and so have no call-graph caller; the
    registration site is found by "a call whose code names this handler",
    and the middleware list is read straight out of that call's code.
  * `build_absence_context()` -- like build_function_context but no dataflow;
    callers included verbatim (the control usually lives in the middleware).

llm_analyzer.py
  * `ABSENCE_SYSTEM_PROMPT` + `ABSENCE_RESPONSE_SCHEMA` -- a 3-step prompt:
    (1) classify the operation, (2) infer the control it requires,
    (3) check that against the guard list.
  * `LlmAnalyzer(mode="injection"|"absence")`; `_parse_absence_findings()`.
  * `_asserts_control_present()` -- drops a finding whose own reasoning
    concedes the control is present or legitimately delegated to a caller.
  * `_clean_vulnerability_type()` now also normalises snake_case
    ("missing_access_control" -> "Missing Access Control").

cli.py: `--mode injection|absence|both`. In `both`, one LLM pass per mode,
findings merged.

Verified end-to-end on NodeGoat: mode runs, the contradiction guard and the
dedup both fire. Known weakness at this point (expected -- tune on the corpus,
not here): the local model over-reports DAO methods as missing-control, and
context prioritisation by hit-count buries route handlers under DAO files.

D3  --  Mutation harness                                   commit d8c4cdc
--------------------------------------------------------------------------------
Goal: turn real Express apps that HAVE working access controls into labelled
missing-control positives by removing one control at a time. Each removal is
scripted, so the ground truth is exact (file, line range, route, control
class) with no human judgement.

New: src/cpgvd/mutation.py -- five operators, regex + brace-balanced text
(NOT an AST; no JS-parser dependency):
  M1  drop an access-control middleware argument from a route registration
      -- one mutation per removable middleware, classified by name
      (auth vs admin/role). Only the prefix up to the handler is rewritten,
      so an inline-function handler body is left byte-for-byte intact.
  M2  drop an ownership comparison `if` (condition names req.user + an
      owner/userId field with a comparison; body is denial-shaped)
  M3  drop a role/privilege check `if`
  M4  drop a session-validation `if`
  M5  drop an input-validation guard sitting within ~60 lines above a DB write
      (an errors-check `if` block, or a standalone validator call)

  * Operator vocabulary is kept SEPARATE from control_absence.yaml on purpose
    -- if the mutator and the detector shared pattern definitions the
    evaluation would be circular.
  * Line-count preserving: removed lines become blank, so a record's
    start_line/end_line are valid against BOTH the original file and the
    mutant -- scoring findings against labels needs no offset bookkeeping.
  * `mutation_applied()` context manager applies a mutation in place and
    restores the exact original bytes.
  * `verify_mutations()` runs `node --check` on every mutant and drops any
    that no longer parses.

models.MutationRecord: id, app, repo, commit_sha, operator, control_class,
file, line range, route_path, original_text, mutated_text, note.

src/cpgvd/corpus.py: JSONL label I/O (`write_labels` / `read_labels`),
`split_by_app()` (stable per-app SHA-256 hash -> holdout; deterministic and
independent of collection order, so re-collecting apps never reshuffles an
app between train and holdout), `summarize()`.

cli.py: `cpgvd corpus mutate <repo>` -> corpus/labels/<app>.jsonl;
`cpgvd corpus stats` -> totals + the by-app split.

Dry run on real NodeGoat: 19 mutations, all survive `node --check`
(16 M1, 3 M4). M2/M3/M5 = 0 because NodeGoat centralises routing with no
per-route inline ownership checks.

D4  --  Reusable pipeline + the evaluation runner          commits 6229fdd, fba4150
--------------------------------------------------------------------------------
Goal: finish B3 (control-absence mode) and build the runner the whole corpus
feeds into.

New: src/cpgvd/pipeline.py -- the analysis pipeline (CPG -> Joern -> context
-> LLM) as a reusable unit with the Joern server INJECTABLE. cli.analyze is
now a thin wrapper (~130 lines removed from cli.py). `run_pipeline(...,
client=<shared>)` reuses one Joern server across many repo states -- this is
the D1 "one server across runs" item, landed where it actually pays off
(a cold JVM per run is ~15s of pure overhead; the 600-mutant eval would
otherwise spend hours just starting JVMs).

Per-route absence context (context_extractor.build_route_absence_context):
ONE candidate per `app.get(...)` REGISTRATION rather than per method. A
centralised router is one `<module>` method with dozens of routes, so a
per-method context is the whole router and the model cannot localise a
single dropped `requireAuth`. The new context is anchored on the
registration line (so it matches an M1 label), carries that route's
middleware list + the resolved handler body (`_resolve_handler` maps
`ctrl.displayFoo` -> its method) + guards on either.
`_split_call_args` parses the registration call (brace/string aware; an
inline handler stays one argument). Guard-scanning refactored into
`_GuardAcc` + `_scan_guards_*` helpers.
pipeline.extract_contexts splits route triggers (per-registration) from the
rest (per-method, e.g. DAOs).

New: src/cpgvd/evaluation.py -- `run_eval()`:
  1. Analyse the UNMUTATED tree first. Every finding there is a false
     positive (the negative control the plan calls non-negotiable -- the
     false-positive rate on unmutated originals).
  2. Per mutation: apply -> analyse -> score -> restore, all under ONE Joern
     session.
  3. A finding is a hit if it lands within `--match-window` lines of the
     removed control, same file. Two recall numbers:
       - `recall`      : the finding is NEW (not a line the baseline also
                         flagged) -- the detector noticed the *removal*.
                         This is the discriminative number.
       - `recall_raw`  : any finding lands there, baseline suppression
                         ignored -- the ceiling when the baseline is noisy.
  4. P / R / F1 overall and per operator / control class.

models: `MutationEvalResult`, `EvalSummary`, `EvalReport`.
`AnalysisReport` gains `contexts` -- `analyze` now persists the analysed
contexts (guard_evidence + node ids) into report.json so a finding is
checkable against what the model actually saw.

cli.py: `cpgvd corpus eval <labels.jsonl>`.

D4 smoke test on NodeGoat (3 M1 mutants, max_contexts 6):
  * pre per-route-context fix : recall 0/3, 5 FP on the unmutated original.
    Cause: the whole-router context (above). NOT a harness bug.
  * post fix (4 M1 mutants, max_contexts 10) : recall 4/4 = 1.00,
    precision 0.12, F1 0.21, 6 FP on the original. The precision is the
    known local-model weakness -- it flags NodeGoat's genuinely public
    routes (/login, /signup, /logout) as missing-control.

Precision fix -- public-route awareness (4 layers, all general, none tuned
to NodeGoat):
  1. models.is_public_route() -- classifier for conventionally-public
     endpoints: the auth flow itself (login, logout, signup, register,
     reset/forgot password, verify email, OAuth callback), health/status/
     metrics probes, and static-asset paths.
  2. to_absence_prompt_text() adds an explicit NOTE for a public route.
  3. ABSENCE_SYSTEM_PROMPT step 2 carves out public endpoints (required
     control = none unless the handler exposes another user's data or makes
     a privileged change).
  4. Post-filters in _parse_absence_findings:
       - _required_control_is_none : drop a finding when the model's own
         `required_control` schema field is "none" / "n/a" / "public".
         NodeGoat's `/` finding literally had required_control="none" and
         still emitted -- the same self-contradiction as
         _asserts_control_present, via the schema field, and it generalises
         past public routes.
       - _public_route_finding_is_noise : drop a public-route finding unless
         its *reasoning* (not its boilerplate `description`, which pads
         "could allow privileged actions" onto every finding) cites
         sensitive-data exposure or a privileged change.
  FunctionContext gains `route_path`.

NodeGoat eval across the D5 fixes (4 M1 mutants, max_contexts 10):
       fix stage            baseline FP   precision   F1
  ---------------------------------------------------------
  pre                            6           0.12     0.21
  + public-route filter          2           0.23     0.35
  + tightened filters            1           0.375    0.50
  recall stayed 0.75: the one miss and the one remaining FP are both
  `/contributions`, which the model insists needs *role* control when it
  has isLoggedIn -- an ambiguous route, n=1 on a held-out app.

GitHub corpus collection -- src/cpgvd/corpus_collect.py:
  * GitHubClient (pagination + rate-limit backoff; reads GITHUB_TOKEN /

  * Repo search (JavaScript, stars, recent, not archived) -> screen each

  * cli `corpus collect`: search -> clone -> mutate -> verify. `--min-mutations`

3. EVALUATION RESULTS SO FAR
================================================================================

The paced eval run was started and then stopped after the first app. One
grounded data point is saved (corpus/eval/bradtraversy__storybooks.json):

  storybooks, grounded, 11 M1 mutants
  --------------------------------------------------
  recall (discriminative)  0.18   (2/11)
  recall_raw               0.73   (8/11)
  precision                0.03
  F1                       0.06
  FP on unmutated original 5

Reading: the detector LOCALISES 8 of the 11 removed `ensureAuth` guards
(recall_raw 0.73) but flags the same protected routes in the BASELINE too
(it wants an in-handler ownership check even when route-level auth is
present), so:
  * precision craters -- every mutant emits ~5 findings, mostly noise
  * the real detection is suppressed as "flagged anyway" -> discriminative
    recall drops to 0.18

This is the SAME failure seen on NodeGoat's `/contributions`. It is the
current bottleneck for every downstream number (B5 grounded-vs-raw, B6
held-out, B7 ratios). It is a prompt-tuning problem: the absence prompt
over-weights "handler has no ownership `if`" and under-weights "route has an
auth guard". Fix against the corpus TRAIN split, then re-run.

Remaining eval work: 9 app-runs (grounded hagopj13/keystone/madhums/sahat +
all 5 raw) = 73 mutant-runs. `bash scripts/run_corpus_eval_paced.sh 12 1200`
resumes from hagopj13.

7. KNOWN ISSUES / NEXT MOVES
================================================================================

BLOCKER 1 -- corpus size. 5 apps / 96 instances vs B4's 25/500. Needs a
  GITHUB_TOKEN so `cpgvd corpus collect` can use the repo search.

BLOCKER 2 -- absence-detector over-flagging (the storybooks / NodeGoat
  /contributions pattern). The detector demands MORE control than exists:
  it reports "missing ownership check" on routes that already have
  route-level authentication. This tanks precision directly and suppresses
  real M1 detections. Fix: strengthen ABSENCE_SYSTEM_PROMPT so that when
  guard_evidence shows authentication is present, authentication is
  satisfied and ownership/authorization is only reported with a concrete
  cross-user access path; add a matching filter. Tune against the 3-app
  train split, verify on storybooks + NodeGoat (fast), THEN run the full
  paced eval.

Also open, smaller:
  * M1 should skip `passport.authenticate(...)` on `*/callback` and public
    routes -- an OAuth callback needs it to function, it is not an access
    control (storybooks label #1 is invalid for this reason; same class as
    the parse-server M3s).
  * `analyze --mode both` does not cross-dedupe injection vs absence findings.
  * The stale-Joern-server-on-port-8080 situation: JoernServer does not
    verify its own subprocess bound the port; if a previous server is
    lingering, a new run silently attaches to it. Harmless so far but worth
    a guard.

D7  --  Stop the over-escalation                          commit 0b00a73
--------------------------------------------------------------------------------
The storybooks / NodeGoat-`/contributions` failure: authentication IS present
on the route, but the model reports "missing ownership/authorization" purely
from the absence of an `if (resource.owner === req.user)` line. This tanked
precision directly and (via baseline suppression) discriminative recall --
storybooks grounded was recall 0.18 / recall_raw 0.73 / precision 0.03.

- ABSENCE_SYSTEM_PROMPT: when `guard_evidence` contains an AUTHENTICATION
  entry, authentication is SATISFIED -- do not report missing authentication,
  and do not escalate to missing ownership/authorization just because there
  is no explicit ownership `if`. Report ownership/authz ONLY with a concrete
  cross-user access path (name the resource, the id parameter, why it is
  per-user). Step 2 also notes that not every resource is per-user (a shared
  list, a catalogue item, a lookup table need no ownership check).
- llm_analyzer._over_escalation_is_noise: drop an ownership/authorization
  finding when the context has an auth/session guard AND the reasoning cites
  no concrete cross-user access (_SENSITIVE_ON_PUBLIC_RE doubles as that
  detector).

D7  --  H3 compression + H5 grounded-findings ratios      commit 3848706
--------------------------------------------------------------------------------
src/cpgvd/metrics.py -- both cheap local computations, no Joern/LLM:
  * compression_summary: slice LoC vs file LoC vs repo LoC and the ratios
    (H3 -- how much the CPG slice compresses what the model must read).
  * grounded_findings_ratio: fraction of findings whose cited line range
    overlaps what the model was actually shown (H5). Raw contexts count the
    whole file.
Wired into `analyze` (AnalysisReport.metrics) and `corpus eval`
(EvalSummary.compression / .grounded_findings, surfaced in _aggregate.json).

D8  --  Semgrep rule-only baseline (comparative axis 2)   commit c8291f7
--------------------------------------------------------------------------------
rules/semgrep/unprotected_route.yml -- flags an Express route registered with
the handler directly after the path (no middleware). The strongest a
pattern-only tool can do for missing route-level access control.

- src/cpgvd/baselines.py: run_semgrep() -> Finding objects in the same shape
  the LLM detector produces, so evaluation.py scoring applies unchanged.
- evaluation.run_eval_semgrep(): same baseline + per-mutant + score loop,
  no Joern, no LLM.
- cli `cpgvd corpus eval-semgrep <labels>` -> corpus/eval/<app>-semgrep.json
  + _aggregate-semgrep.json.
- pyproject: [baseline] extra (semgrep).

RESULT (5-app corpus, 96 mutations):
  semgrep : precision 0.01, recall 0.53, FP-on-originals 85
  by operator: M1 0.76 (44/58 -- misses M1s that leave >=2 middlewares),
               M2 0.00, M4 0.00, M5 0.27 -- a rule cannot see a removed `if`.
This is the "a pattern match is not a vulnerability" straw man the thesis
argues against: high M1 recall, zero M2-M4 recall, precision destroyed by
public / no-middleware routes.

Section 10 -- D10: held-out benchmark (B6), 2026-08-30
================================================================================

The mutation corpus (Sections 5-9) is built from the same apps the rules and
prompt were tuned on. B6 is the other half of the evaluation: a held-out app
scored against an EXTERNAL authority, never tuned against.

Chosen app: OWASP Juice Shop, tag v17.3.0
(commit 1867b926c5f50e4e692dc9c8f61821413cebe0cd), cloned to
corpus/repos/juice-shop (git-ignored).

Ground truth: Juice Shop publishes its own vulnerability list in
data/static/challenges.yml, and marks the vulnerable line in-source with
`// vuln-code-snippet vuln-line <challengeKey>` comments. corpus/heldout/
juice-shop.yaml maps the subset our control-absence detector can be scored on
-- 8 challenges in the Broken Access Control / Improper Input Validation /
Sensitive Data Exposure categories whose missing control sits at one route
registration or handler entry:

  changeProductChallenge        authorization  server.ts:361   (PUT authz commented out)
  exposedMetricsChallenge       authorization  server.ts:697   (/metrics unguarded)
  accessLogDisclosureChallenge  authorization  server.ts:280   (/support/logs/:file)
  basketAccessChallenge         ownership      routes/basket.ts:15
  basketManipulateChallenge     ownership      routes/basketItems.ts:19
  forgedReviewChallenge         ownership      routes/createProductReviews.ts:14
  forgedFeedbackChallenge       ownership      server.ts:388
  registerAdminChallenge        validation     server.ts:406

Deliberately excluded (documented in the yaml header): client-side-only route
guards (adminSectionChallenge), crypto/storage, SQL/NoSQL-injection logins,
CSRF, SSRF, security-question reset logic, weak-password policy -- none is a
missing server-side control the detector's rules can see.

Note: server.ts line ~23 of models.py's _PUBLIC_ROUTE_RE lists `metrics` as a
conventional probe, so the grounded detector is EXPECTED to suppress
exposedMetricsChallenge. Kept as a label anyway -- it is an honest illustration
of that heuristic's precision/recall trade-off.
